Customers Module — User Guide

The operational dashboard for buyer registrations. Monitor counts, manage allotments, record offline payments, and process cancellations.

Portal: Admin URL: /admin/customers Last Updated: 2026-05-21 BRD: ADMIN-BRD-Customers FRD: ADMIN-FS-Customers (+ Milestones, UnitSwap, Parking)

Overview

The Customers module is the default landing page after Admin login. It surfaces six live KPI cards summarising registration health, a paginated registration table, and a set of context-sensitive row actions (trash icon, three-dot menu) that drive 15+ distinct workflows ranging from read-only browsing through to irreversible unit cancellation.

Primary Actor: Admin / Sales Manager Admin (same permissions) Secondary Actor: Buyer (notifications only) System Actor: KPI refresh · audit log · Mavis · LSQ · WebSocket · Kaleyra

Color coding used throughout this guide

READ — non-destructive, no DB writes
REVERSIBLE WRITE — value can be re-set
IRREVERSIBLE WRITE — cannot be undone in-app
SYSTEM — automated downstream effect

Feature Walkthroughs

1. Registration Dashboard

READ

What it does. Renders six KPI cards plus the registration table. KPIs are live and update as the underlying data changes.

Who can use it: Admin / Sales Manager Admin When available: Always (default landing page after login)

The six KPI cards

Card Definition
Registered Booked Offline + Booked Online + Registered + Inactive (NOT just "Registered" status alone)
Inactive Registrations Registrations set to inactive
Cancelled Registrations Registrations that have been cancelled
KYC Pending (Booked) Buyers who have paid and booked but not completed KYC
Confirmed (Paid + KYC) Buyers who have both paid and completed KYC
Active Towers Live count from the Config module's tower configuration

Step-by-step

  1. Log in to the Admin Portal. The Customers dashboard opens automatically.
  2. Read the six KPI cards at the top.
  3. Scroll to the registration table. The heading shows the true total (for example, 9,672 Registration Records).
  4. Browse rows newest-first.

Expected result. Six KPI numbers render with correct values. Table heading shows total count. Rows render with all 10 columns.

Buyer notifications

None. Read-only.

Reviewer checklist
  • All 6 KPI cards visible at top of page.
  • "Registered" KPI = sum of Booked Offline + Booked Online + Registered + Inactive (verify against DB query).
  • "Active Towers" KPI matches Config module's active tower count.
  • Table heading shows total record count, not visible row count.
  • Rows ordered by createdAt descending (newest first).
  • "Allocation Opened" banner renders unconditionally (known UI bug — assert presence only).

2. Search by Phone

READ

What it does. Live-filters the registration table by buyer phone number.

Who: Admin / SM Admin When: Always

Step-by-step

  1. Locate the Search by Phone field at the top right of the table.
  2. Type the buyer's phone number (full or partial).
  3. The table filters to matching registrations.
  4. Clear the field to restore the unfiltered list.

Expected result. Filter applies on input. KPIs remain unchanged (KPIs are global, not filter-scoped).

Buyer notifications

None.

Reviewer checklist
  • Partial-match returns relevant rows.
  • Clearing the field restores full list without page reload.
  • KPIs unaffected by phone search.
  • Search persists across pagination clicks within the same session view.

7. Download Export

READ

What it does. Exports the complete registration dataset to RegistrationData.xlsx. Always includes all records, regardless of active filters.

Step-by-step

  1. Click the Download button (top right area).
  2. The file downloads to the browser's default download location.
  3. Open RegistrationData.xlsx in Excel.

API: GET /api/v1/admin/dashboard/all-buyers?isDownload=1 or GET /api/v1/admin/export/registrations. File contains 17 columns.

Note

Filters on screen do NOT affect what is exported — the export always returns every record.

Buyer notifications

None.

Reviewer checklist
  • File name is exactly RegistrationData.xlsx.
  • Row count in XLSX equals total registration count in DB.
  • All 17 columns present.
  • Download action is audit-logged (admin user ID + timestamp).

8. View Milestones

READ

What it does. Opens the Milestone Payment Schedule for a Booked unit at /admin/milestone?rn=&uid=. Lists every construction-linked milestone with Paid / Partial / Pending pill, amounts, and outstanding balance.

Who: Admin / SM Admin When: Three-dot menu visible only when isBooked === true

Step-by-step

  1. Locate a Booked Online / Booked Offline row.
  2. Click the three-dot (…) icon. Select View Milestones.
  3. The Milestone Payment Schedule page opens.
  4. Read the schedule. Future-dated milestones render no status; past milestones show Paid / Partial Payment / Pending pills.
  5. Click Back to Customer Listing (top-left) to return — page scrolls back to the customer table.

Expected result. Page renders with header card (Registration No. + Unit No.) and milestone table. Empty if KYC not yet submitted.

Note

Status pills hide for milestones whose startDate is in the future. The special row ml-or with total = 0 renders blank.

Buyer notifications

None. This is a read-only page.

Reviewer checklist
  • Menu item appears only on Booked rows.
  • URL contains both rn and uid query params.
  • Empty state correctly shown when KYC not submitted.
  • Pill rules: balance <= 0 → Pending; 0 < balance < total → Partial; balance >= total → Paid (where balance semantically means "amount paid").
  • "Back to Customer Listing" returns to /admin/dashboard?scrollTo=customerTable.

10. Home Loan Approval

REVERSIBLE WRITE

What it does. Admin-approves a buyer's home loan. Sets loanApprovalStatus = admin_approved and approvalSource = admin. Unlocks the HOME_LOAN offer discount for that buyer during allocation.

Who: Admin / SM Admin When: Always (any row state). Current loanApprovalStatus must be pending or null.

Step-by-step

  1. Locate the buyer's row in the Customers table.
  2. Click the three-dot (…) menu. Select Home Loan Approval.
  3. In the modal, flip the toggle to ON.
  4. Click Submit.

Expected result. Buyer's home loan status updates to "Admin Approved". HOME_LOAN discount becomes eligible at next allocation campaign.

Buyer notifications

Kaleyra SMS + WhatsApp confirming home loan approval.

System side-effects

Audit log entry · LSQ activity sync to buyer's CRM record.

Reviewer checklist
  • Menu item available on every row, regardless of allocation status.
  • Toggle visible inside modal; defaults to OFF.
  • After submit, the row reflects "Approved" home loan status.
  • admin_rejected loans hidden from the home-loan indicator (only pending / approved / admin_approved shown).
  • SMS + WhatsApp delivered to buyer's mobile.

11. Update Parking Details

REVERSIBLE WRITE

What it does. Enables / disables additional parking for a Booked unit and sets parking count (1–500 slots) plus per-slot amount. Updates the typology parking pool by the delta.

Who: Admin / SM Admin When: Three-dot menu visible only when isBooked === true

Field schema

Field Validation
additionalParkingEnabled Boolean toggle. Required (both frontend and backend).
parkingCount Integer. Frontend: required, min 1, max 500. Backend: notRequired() (known gap).
parkingAmount Per-slot amount. Frontend: required, positive. Backend: notRequired().

Step-by-step

  1. Locate a Booked row. Click the three-dot (…) menu.
  2. Select Update Parking Details. The Parking Details modal (600px) opens.
  3. Toggle Additional Parking Enabled ON. Count + Amount fields appear.
  4. Enter Parking Count (integer 1–500).
  5. Enter Parking Amount (per slot). The Total Parking Amount preview updates automatically.
  6. Click Submit.
  7. To disable: flip toggle OFF — both fields clear automatically. Submit.

Backend checks on submit: delta against current count must be non-zero; typology parking pool must have capacity for positive deltas.

Expected result. Toast "Parking details updated successfully". Modal closes. Table refetches.

Warning — backend validation gap

The backend Yup schema marks parkingCount and parkingAmount as notRequired(). An API-layer client bypassing the UI could submit {enabled: true, count: 0, amount: 0} and it would be coerced to 0/0. Frontend Formik is the only enforcement layer for "count and amount required when toggle ON".

Buyer notifications

None. The buyer will see updated parking only after refreshing their portal view.

System side-effects

auditActions.ADMIN_UPDATE_PARKING emitted. Parking pool availableParkingSpots decremented (or incremented) by delta. No milestone schedule regeneration.

Reviewer checklist
  • Menu item present only on Booked rows.
  • Existing parking pre-fills the modal when isParkingSelected = 1.
  • Toggle OFF clears both fields client-side.
  • Submit blocked when count outside 1–500 or non-integer (frontend Formik).
  • "No change in parking count" error on no-op delta.
  • "Available parking count (X) is less than required (Y)" error on pool exhaustion.
  • API regression test asserts the documented backend gap is currently still present.
  • Milestone schedule remains unchanged after update.

12. Record Offline Milestone Payment

REVERSIBLE WRITE

What it does. Posts an admin-recorded offline payment for a payable milestone. Submits 11 multipart fields including a mandatory paymentProof file. Mirrors the SM Portal offline payment flow.

Who: Admin / SM Admin When: Offline Payment button visible when milestoneKey !== 'ml-or' OR total !== 0, startDate in past, and outstanding > 0

Field schema (11 fields, all multipart/form-data)

# Field Required Notes
1 registrationNumber Yes Auto from URL ?rn=
2 milestoneKey Yes e.g. ml-or, ml-hcf
3 milestoneId Yes Integer
4 amount Yes > 0. GST mode: must equal gstOutstanding (±0.01)
5 paymentType Auto 1 Principal Full · 2 Principal Partial · 3 GST · 4 HCF Full · 5 HCF Partial
6 paymentMethod Yes NEFT / Cheque / Cash / CC / DC / UPI
7 transactionId Yes Free text
8 transactionDate Yes Cannot be in the future
9 comments No Max 500 chars
10 paymentProof Yes .pdf / .jpg / .jpeg / .png · single file
11 paymentFor Conditional Principal / GST radio. Rendered only when non-HCF AND both legs outstanding > 0.

Step-by-step

  1. Open View Milestones (Feature 8) for the booked unit.
  2. On any past-dated milestone with outstanding balance, click Offline Payment.
  3. The Offline Payment drawer (600px) opens.
  4. If non-HCF and both principal + GST outstanding: pick Payment For (Principal or GST).
  5. Enter Amount (auto-locked in GST mode to gstOutstanding).
  6. Pick Payment Method (NEFT / Cheque / Cash / CC / DC / UPI).
  7. Enter Transaction ID.
  8. Pick Transaction Date & Time (cannot be after now).
  9. Optionally enter Comments (max 500 chars).
  10. Upload Payment Proof (required) — PDF, JPG, JPEG, or PNG.
  11. Click Submit.

Expected result. Toast "Offline payment submitted successfully". Schedule refetches.

Buyer notifications

None. No SMS / WhatsApp / email dispatched. Buyer sees the updated payment status on next portal refresh.

System side-effects

Audit log emitted on backend. Milestone tracking record updated. paymentProof file stored.

Reviewer checklist
  • Offline Payment button hidden when outstanding ≤ 0.
  • Offline Payment button hidden for future-dated milestones.
  • Submit blocked client-side when paymentProof empty.
  • GST mode: amount input disabled and pre-filled with gstOutstanding.
  • HCF milestones: no Payment For radio shown.
  • Transaction Date picker disables future dates.
  • 5MB file size note is informational only (client does not enforce).
  • Multipart POST to adminMilestonePaymentOffline contains all 11 fields.

13. Cancel Unit (Booked rows)

IRREVERSIBLE WRITE

What it does. Cancels the allotted unit (the RegistrationUnit) for a Booked row. Parent Registration is untouched. Sibling sub-registrations remain intact. Releases the unit back to inventory.

Who: Admin / SM Admin When: Trash icon active when row is Booked Online / Booked Offline (status=WINNER + allocationTransactionId)

Step-by-step

  1. Find the Booked row in the table.
  2. Click the trash icon in the Actions column. Tooltip reads "Cancel Unit".
  3. A confirmation modal opens titled "Please make sure that following actions are completed?".
  4. Tick both attestation checkboxes:
    • Activity - Token, Form, Booking deleted (CRM cleanup)
    • Mavis - Booking entry deleted (ERP cleanup)
  5. The Submit button enables once both are checked.
  6. Click Submit.

Expected result. Toast "Unit cancelled successfully". RegistrationUnit cancelled. Unit released.

Warning — irreversible

There is no in-app undo. Use only for test records or confirmed cancellations. CRM and Mavis cleanup must already be done out-of-band — the checkboxes are admin attestations, not triggers.

Buyer notifications

None (Kaleyra is not invoked on this branch).

System side-effects

Audit log entry · WebSocket cache invalidation for the released unit · KPI counts refresh.

Reviewer checklist
  • Trash icon tooltip on Booked row reads "Cancel Unit".
  • Submit disabled until both checkboxes ticked.
  • RegistrationUnit row status changes; parent Registration unaffected.
  • Sibling sub-registrations (e.g. -B, -C of same GHNG) unaffected.
  • Released unit becomes available again in WebSocket pool.
  • Rows in REFUND status show "-" instead of any action.

14. Cancel Registration (Registered / Waitlisted rows)

IRREVERSIBLE WRITE

What it does. Cancels a Registered or Waitlisted registration (no unit allotted) and refunds the ₹999 registration confirmation amount back to the buyer's original payment method.

Who: Admin / SM Admin When: Trash icon active when row is Registered or Waitlisted (no unit allotted)

Step-by-step

  1. Find the Registered / Waitlisted row.
  2. Click the trash icon. Tooltip reads "Cancel Registration".
  3. The confirmation popup shows the unit details (if any) and the refund amount ₹999.
  4. Click the red Cancel Registration button.

Expected result. Toast "Registration refunded successfully". Status changes to Cancelled. Refund transaction created for ₹999. KPI counts refresh.

Warning — irreversible

The refund cannot be undone in-app. Confirm the buyer's identity and refund eligibility before clicking the red button.

Buyer notifications

Kaleyra SMS + WhatsApp with cancellation + refund confirmation.

System side-effects

RegistrationUnit.allocationStatus → cancelled · Refund transaction created · Unit released back to inventory · WebSocket cache invalidated · KPI counts refreshed · Audit log entry.

Reviewer checklist
  • Trash icon tooltip on Registered / Waitlisted row reads "Cancel Registration".
  • Modal shows ₹999 as the refund amount.
  • Red "Cancel Registration" button is the confirm action.
  • Refund transaction is recorded against the buyer's original payment method.
  • Kaleyra SMS + WhatsApp delivered.
  • Registered KPI decrements; Cancelled KPI increments.

15. Assign Unit / Offline Booking

IRREVERSIBLE WRITE

What it does. Assigns a unit to a Registered (no-unit) row and captures an offline payment transaction in a single submission. Bypasses the online payment gateway — used when the buyer paid by bank transfer, cheque, UPI, etc.

Who: Admin / SM Admin When: Three-dot menu visible when row is Registered (allocationStatus=available) AND no unit allotted

Field schema

Field Required Notes
Tower Yes Dropdown — all project towers
Unit Yes Available / Reserved units only; format <Unit No> – <Typology>
Transaction ID Yes Bank / cheque reference
Mode of Transaction Yes UPI / NEFT-RTGS / Cheque / Cash
Booking Amount Yes > 0. System does NOT validate against expected amount.
Transaction Date Yes Default: today
Upload Proof No Optional — image or PDF. Stored to Azure Blob.

Step-by-step

  1. Locate a Registered row with no allotted unit.
  2. Click the three-dot (…) menu. Select Assign Unit.
  3. The offline booking modal opens.
  4. Pick Tower from the dropdown.
  5. Pick Unit (Available or Reserved only; format 1203 – 2 BHK Rise Home).
  6. Enter Transaction ID / Reference No., Mode, Booking Amount, Transaction Date.
  7. (Optional) Upload payment proof — cheque image, transfer screenshot, voucher.
  8. Click Submit.

Expected result. Unit marked BOOKED. Registration status moves to Confirmed. KPI Registered decreases; Confirmed / Booked increases.

Warning — booking amount not validated

The system does not check the booking amount against commercial terms. Enter the correct amount — there is no safety net.

Warning — unit availability re-check at submit

If another admin allots the unit between modal open and submit, the request fails with "Selected unit is no longer available. Please choose another unit."

Warning — single-booking constraint

If the registration already has an active unit booking: "This registration already has an active unit booking."

Buyer notifications

Kaleyra Email + WhatsApp with unit details and payment acknowledgement.

System side-effects

Insert into payment_transactions (isOffline=1, paymentSource=admin, status=completed) · RegistrationUnit updated to confirmed with allocated tower / floor / unit · Unit.status → BOOKED · WebSocket cache invalidated · Mavis Bookings + Units sync · 3 LSQ activities (Booking Token, Booking, Booking Form) · KPI refresh · Audit log entry.

Reviewer checklist
  • Menu item appears only when allocationStatus = available AND no unit allotted.
  • Unit dropdown shows only Available / Reserved units.
  • All five required fields validated for non-empty + amount > 0.
  • Optional proof upload persists URL on the transaction record.
  • Race-condition error message rendered correctly when unit is taken mid-flight.
  • Mavis Booking + Mavis Unit status updates verified post-submit.
  • All 3 LSQ activities created (out of LSQ scope for automation but audit-log-trace expected).
  • Kaleyra Email + WhatsApp delivered.

16. Unit Swap

IRREVERSIBLE WRITE

What it does. Reassigns a buyer's already-allotted unit to a different unit within the project. Operates at RegistrationUnit level. Used for buyer-requested changes or operational corrections.

Who: Admin / SM Admin When (UI gate): isBooked === true When (backend gates): no active allocation campaign · no Mavis booking row · target unit AVAILABLE/RESERVED · typology mapped · not linked elsewhere

Step-by-step

  1. Prerequisite 1. Confirm no allocation campaign is currently active for the project. Close any open campaign in the Allocation module first.
  2. Prerequisite 2. Delete the Mavis (ERP) booking row for this registration outside the portal.
  3. Prerequisite 3. Delete the CRM Activity records — Token, Form, Booking — for the current allotment.
  4. In the Customers table, locate the Booked row whose unit needs to change.
  5. Click the three-dot (…) icon → Unit swap.
  6. Review the read-only header (Registration No., Current Unit, Apartment Type / carpet area).
  7. Open the Tower dropdown — towers load lazily on first open. Note: list includes inactive towers; pick carefully.
  8. Open the Unit dropdown — populated with AVAILABLE / RESERVED units in that tower. Typology is NOT filtered — confirm the new typology before submit.
  9. Tick both attestation checkboxes:
    • Activity - Token, Form, Booking deleted
    • Mavis - Booking entry deleted
  10. Click Submit.

Expected result. Toast "Unit swapped successfully". Modal closes. Table refetches. New unit BOOKED; previous unit returns to RESERVED (if not consumed elsewhere).

Warning — irreversible, no in-app undo

Verify both the new unit selection and the attested cleanup before submitting. There is no "undo swap".

Warning — milestone schedule NOT regenerated

Backend code path is commented out with developer note "need to discuss". After swap the original unit's milestone schedule and payment transactions remain attached to the registrationUnit — potentially stale if the new typology / pricing differs. Pending product decision.

Warning — open campaign blocks swap

Backend rejects with 400 "Cannot swap unit when campaign is active" if any allocation campaign is open for the project. This is a hard gate — no override.

Warning — typology mismatch allowed

The backend does NOT enforce same-typology swaps. Admin may swap into a different apartment type / carpet area. Confirm acceptance before submit.

Buyer notifications

None. No SMS, WhatsApp, or email is dispatched. Communicate the change out-of-band if business requires.

System side-effects

RegistrationUnit updated: unitId, towerId, typologyId, allocatedTower/Floor/Unit · Reset flags: bookingTokenActivitySubmitted, mavisBookingCreated, mavisUnitUpdated, lsqBookingActivityId, lsqBookingFormActivityId, isKycPdfSubmitted (and KYC-related flags if KYC was submitted) · New unit → BOOKED, previous unit → RESERVED · Redis cache updates · auditActions.ADMIN_UNIT_SWAP emitted.

Reviewer checklist
  • Menu item visible only on Booked rows.
  • Submit disabled until BOTH checkboxes ticked AND a new unit is selected.
  • Tower dropdown loads on first open (lazy).
  • Unit dropdown filtered by towerId + projectId + status IN (AVAILABLE, RESERVED) — no typology filter.
  • Open campaign correctly rejects with the documented 400 message.
  • Mavis row presence rejects with the documented 400 message.
  • Target unit linked elsewhere returns 409.
  • Milestone schedule confirmed unchanged after swap (open gap).
  • No Kaleyra dispatch (verify via API trace).
  • Audit row ADMIN_UNIT_SWAP written server-side.

17. Bulk Cancel Units

IRREVERSIBLE WRITE

What it does. Cancels multiple sub-registrations (units) at once. Per-row gates from Cancel Unit apply to each entry. Useful for cleaning up cancelled allotments where a single buyer holds several sub-registrations.

Who: Admin / SM Admin When: Always (button always visible)

Step-by-step

  1. Click Cancel Bulk Units above the table.
  2. Select the sub-registrations to cancel.
  3. Confirm the bulk action.

Expected result. All selected sub-registrations cancelled. Each row inherits the same per-row gate as Cancel Unit (Feature 13).

Warning — irreversible per row

Each cancellation in the bulk is irreversible. There is no transaction rollback if some succeed and some fail — partial outcomes are possible.

Buyer notifications

Inherited from Cancel Unit (Feature 13) — none on this branch.

Reviewer checklist
  • Button visible always.
  • Selection model is multi-select.
  • Per-row gates from Cancel Unit apply.
  • Audit log entries written per cancelled row.
  • Partial-failure outcome handled — failed rows reported back to admin.

Reviewer Checklist (Master)

Consolidated checklist for manual QA review of the Customers module. Each feature's specific checklist is also embedded in its individual walkthrough above.

Cross-feature regression checks
  • All six KPI cards render with correct definitions and live counts.
  • "Allocation Opened" banner renders unconditionally (known UI bug — verify presence, not state binding).
  • Trash icon tooltip context-switches between "Cancel Unit" (Booked) and "Cancel Registration" (Registered / Waitlisted).
  • Three-dot menu items are context-sensitive per the visibility matrix.
  • Download export ignores active filters — exports full dataset.
  • REFUND rows show "-" in the Actions column.
  • Pagination range indicator updates on page-size change.
  • Unit Swap milestone-schedule regeneration is NOT triggered (open gap — verify schedule stable post-swap).
  • Parking validation gap: backend Yup is notRequired() for count + amount (verify API regression).
  • Kaleyra dispatch only on Cancel Registration, Home Loan Approval, Assign Unit (verify NO dispatch on the others).
  • Audit log rows written for all write operations.
  • WebSocket cache invalidation on Cancel Unit, Cancel Registration, Unit Swap, Assign Unit.
  • Mavis sync only on Assign Unit (and pre-deleted by admin for Unit Swap).
  • LSQ sync only on Home Loan Approval and Assign Unit.
Known issues to be aware of during review
  • Allocation Opened banner is statically hardcoded (CustomerTable.jsx L1602). Flagged for engineering remediation.
  • Unit Swap milestone schedule regeneration commented out with developer note "need to discuss" (registration-unit.service.js L208–211). Open product decision.
  • Parking backend validation gap: count and amount can be sent as 0 via direct API and would be coerced — only frontend Formik enforces.
