## 1. Module Overview

### Purpose
The Allocation module governs the end-to-end lifecycle of how a registered buyer is matched to a unit, holds it, pays the booking-confirmation amount, and is converted into a "WINNER" (booked) record. It supports three allocation modes — **STATIC**, **DYNAMIC**, and **PHYSICAL_EVENT** — orchestrated through an **Allocation Campaign** entity.

### Scope (from source)
Admin Portal Allocation feature surface includes:
- Create / update / terminate an Allocation Campaign (`POST/PUT /api/v1/admin/allocation/campaigns`)
- List campaigns, get campaign detail, list dynamic rounds, export allotments to Excel
- Notify Physical-Event registrants with QR codes
- Compute dynamic unit cost-sheet and payment schedule (`GET /api/v1/admin/allocation/unit-details`)
- Manual reconcile of allocation payment by reference (`POST /api/v1/admin/allocation/transaction/check`)
- Downstream (buyer / SM) order creation, payment callback, KYC submission — used by Admin via shared services.

### Roles touching the feature (`source-code/backend/src/constants/global.js:31-37`)
`admin`, `user`, `cp`, `sales_manager_admin`, `sales_manager`.
Admin-portal endpoints require `protect, restrictTo('admin')` middleware — `source-code/backend/src/routes/admin.routes.js:53`.

### 3.9 POST `/api/v1/admin/allocation/transaction/check` — Reconcile Transaction by Reference

Flow:
1. Verify with payment gateway via `paymentGatewayService.verifyByReference(referenceNo, { updateDb:false, fallbackStatus, forcedCancel })` `// Source: allocation.service.js:271-275`
2. Update transaction status (locking + tx via gateway service): `paymentGatewayService.updateTransactionStatus(referenceNo, TransactionTypeId.UNIT_ALLOCATION, raw, options)` (line 283-288). 404/500 short-circuit.
3. Re-fetch user, parse `transaction.metadata.formData.unitRequested` (array enforced).

5. Else → `handleExpiredHoldOrFailedPayment` (line 140-189) which:

   - For `HOLD` unit older than **20 minutes** → `resetUnitStatuses`
6. `resetUnitStatuses` (line 192-263):

   - Raw SQL `UPDATE registration_units SET status='ALLOCATED', unit_id=NULL, tower_id=NULL …` (line 210-230) — restores typology by name lookup

## 6. Status Flows & State Machines

### 6.1 AllocationCampaign.status (`allocation-campaign.model.js:81-85`)
```
NOT_STARTED ──(time enters window | python /campaign/start)──▶ RUNNING
NOT_STARTED ──(admin terminate while upcoming)──▶ CANCELLED
RUNNING     ──(admin terminate while running)──▶ STOPPED
RUNNING     ──(natural completion)──▶ COMPLETED
ANY non-terminal ──(window passed & not updated)──▶ FAILED   (auto on next create attempt; allocation-campaign.service.js:563-570)
ANY non-terminal ──(python /campaign/start failure)──▶ destroyed (campaign hard-deleted; allocation-campaign.service.js:990-1010)
```
Terminal states: `STOPPED, CANCELLED, COMPLETED, FAILED`.

### 6.2 DynamicRound.roundStatus (`dynamic-round.model.js:51-56`)
`NOT_STARTED → RUNNING → COMPLETED`, or `FAILED`. Toggled primarily by the Python orchestrator (not in this Node codebase).

### 6.3 RegistrationUnit.status (`constants/global.js:63-70`)
```
WAITLIST ─┐
          ├──▶ PREALLOCATED ──▶ ALLOCATED ──▶ HOLD ──▶ WINNER ──▶ REFUND
          └─(any time)
```
- `PREALLOCATED` set during campaign creation (`allocation-campaign.service.js:744-748, 828-836`)
- `HOLD` set when order placed (`allocation.service.js:671-674`)
- `WINNER` set in `finalizeAllocationForTransactionV2` (`allocation.service.js:1039`)
- Back to `ALLOCATED` via `resetUnitStatuses` after failed payment or 20-min HOLD expiry (`allocation.service.js:210-230`)

### 6.4 Unit.status
`AVAILABLE → HOLD → BOOKED`, with rollback `HOLD → AVAILABLE` on payment failure (`allocation.service.js:799-802`).

### 6.5 ParkingInventory.status
`AVAILABLE → HOLD → BOOKED`, rollback `HOLD → AVAILABLE` on payment failure (`allocation.service.js:809-814`).

### 6.6 RegistrationUnit.allocationStatus (`constants/global.js:55-61`)
`available | waiting | confirmed | cancelled | refunded`. Set to `confirmed` in `finalizeAllocationForTransactionV2` and `cancelled` in `cancelUserAllocation`.

### 6.7 AllocationCampaignUnit.status (`allocation-campaign-unit.model.js:70-75`)
`AVAILABLE → HOLD → BOOKED`. Set to `BOOKED` during PHYSICAL_EVENT finalize (`allocation.service.js:1177-1182`).

### 6.8 InitialAllotment.status
Observed values: `PREALLOCATED, ALLOCATED, WINNER`. Transitions performed in:
- create-campaign — `PREALLOCATED`
- finalize: existing PREALLOCATED/ALLOCATED → `WINNER`; new WINNER row for DYNAMIC if no prior allotment row exists (`allocation.service.js:1080-1190`)

## 8. Edge Cases & Known Constraints

1. **Bug-suspect in `cancelUserAllocation`** — the validation uses a non-existent fluent `RegistrationUnit.join(...)` chain that is also wrapped in `if (!...)` without `await`. This always short-circuits to truthy (object), so the access check is effectively a no-op. `// Source: allocation.controller.js:56-62`. Tests should assert that a non-owning user cannot cancel another user's allocation.

2. **Hard-coded 20 minutes** for HOLD expiry — used in two places: `handleExpiredHoldOrFailedPayment` (`allocation.service.js:174-177`) and `physical-allocation-release-units.cron.js:14`. Any divergence will create stuck holds.

3. **Hard cap of 20 registrations per unit** for DYNAMIC Excel — `allocation-campaign.service.js:453-457`. PHYSICAL_EVENT explicitly does **not** apply this cap (`validatePhysicalEventAssignedMapping`).

4. **GST band cutoff at ₹45,00,000** — `calculateGstRate` returns 1% for FAV < 45L, else 5% — `allocation.service.js:2527`. Identically used to compute `gstToGovernmentPercentage` in the cost sheet (`allocation.controller.js:590`).

5. **TDS only above ₹45L** — `calculateTdsRate` returns 0 when `finalAgreementValue <= 4_500_000` (`allocation.service.js:2529-2530`); cost-sheet filter drops `ml-tds` row if principal is ≤0 (`allocation.controller.js:797-805`).

6. **Stamp duty hard-coded 7%** of FAV — `allocation.service.js:2553`.

7. **Registration charges default 30000** when not supplied — `allocation.service.js:2539`.

8. **Maintenance charges formula** `10 * carpetArea * 12` with 18% GST — `allocation.service.js:2567-2570`. Returned as `maintenanceChargesWaiver`.

9. **Allocation amount logic** (`allocation.service.js:2517-2522`):
   - `allocationCalcType='PERCENT'` → `originalAllocationAmount = FAV * allocationPercent / 100`; subtract EOI; add GST.
   - `allocationCalcType='AMOUNT'` → use raw `allocationAmount`; no GST split inside this helper.

10. **`paymentPlanVersionId` derivation** — taken from `paymentSchedule.find(item => item.milestoneKey === 'ml-ual')?.versionId` (or nested `typologyMilestone.versionId` for WINNER). If missing, `paymentScheduleAdditionalInfo` is `null`. `// Source: allocation.controller.js:568-576`.

11. **Schedule ID hard-coded to `'schedule-1776945025890'`** in Mavis insert — `allocation.service.js:1536, 3640`. Future change will require both call sites.

12. **`RegistrationUnit.update` with `hooks:false`** in finalize — bypasses Sequelize hooks during WINNER promotion (`allocation.service.js:1060, 1074`). Implication: any hook-based downstream side-effects (audit triggers, etc.) are not fired during finalize.

13. **Python `/campaign/start` failure DESTROYS the campaign** (and its `dynamic_round`) — `markAllocationCampaignFailed` uses `Model.destroy` which combined with `paranoid:true` is a soft-delete. The freshly-uploaded `initial_allotment` rows and `allocation_campaign_units` are **not** explicitly soft-deleted, so they may remain orphaned. `// Source: allocation-campaign.service.js:990-1010`.

14. **Excel error response media type** — endpoint returns `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` with status 400 when validation fails. Test clients must handle binary-error response on the same endpoint they expect JSON. `// Source: allocation-campaign.controller.js:71-77`.

15. **No project-id filter on the "latest campaign" auto-FAIL check** — `allocation-campaign.service.js:548-552` fetches the global most-recent `AllocationCampaign` (no `projectId` filter) before deciding to auto-fail. This may incorrectly block creation across projects. **Test target.**

16. **`getLatestAllocationCampaigns` default projectId** — when no query param, controller falls back to `app.production ? 1 : 2` — `allocation-campaign.controller.js:106`. Non-production defaults to projectId=2.

17. **Razorpay-only manual cancel** — `cancelAllocationOrderService` rejects Easebuzz with `Only Razorpay orders can be cancelled via this endpoint` (`allocation.service.js:426`).

18. **Duplicate Mavis schedule ID** between create-time insert and final update — `'schedule-1776945025890'`. Originally there was multi-typology mapping (commented out at `allocation.service.js:1530-1535`).

19. **Documents schema for KYC LSQ upload** is hard-coded for max 3 co-applicants; further co-applicants silently dropped — `allocation.service.js:2313` (`i < 3`).

20. **OTP master backdoor** — `verifyKycEsignOtp` accepts `otpConfig.adminMasterOtp` as a universal OTP (`allocation.controller.js:966-971`). Logged at INFO level. Must be excluded/secured in UAT/Prod tests.

21. **`registration_units.allocationStatus = cancelled` is decoupled from `status`** — `cancelUserAllocation` updates `allocationStatus` only; `status` (WINNER/HOLD/…) is untouched. Reporting that mixes both columns may diverge.

22. **WebSocket emitter expected but absent** — comments at `allocation.service.js:324, 1698` say `// update websocket and notification`. No `socket.io`/`emit` calls in the read code. — **not found in source code**.

23. **`allocationStatus` enum** has `available, waiting, confirmed, cancelled, refunded`; finalization only ever sets `confirmed`. Other values are written by other modules (refund/cancel).

24. **`allocationBatches` model unused** by allocation campaign code paths read here. `allocation-batch.service.js` only exposes `getActiveAllocationBatch` (consumed elsewhere). Treat batches as a separate sub-feature unless evidence found otherwise.

25. **Allocation `availableForAllocation` flag** is required `true` to create an order (`allocation.service.js:457`). Tests should cover WAITLIST registrations that have this flag toggled.

26. **Park-enabled key** — `master_configs.key = 'park_enabled'` per project, boolean. Order creation (`allocation.service.js:590-595`) and KYC parking allocation (`allocation.service.js:1970-1979`) both gate on this.
