## Default QA Flow


Mandatory execution order for any new module or feature. Agents and skills are invoked in strict sequence. No step may be skipped.

### Phase 1 — Requirements (BA Agent)

1. BA Agent reads the relevant BRD/FRD section for the module from .claude/docs/hoabl-knowledge-base/
2. Calls skill: manual-tester to produce structured test cases (positive + negative) and test data specs
3. Hands output to QA Agent for review via skill: test-case-reviewer
4. Output: reviewed and approved TestCases.xlsx
   — Sheet 1: manual test cases with positive/negative per user journey
   — Sheet 2: automation candidates
   — Bug report sheet template

### Phase 2 — Element Locator Map (Tech Lead Agent)

5. Tech Lead Agent reads the approved test cases and scans portal source code (Strapi excluded entirely)
6. Calls skill: locator-map-builder to generate/update the Element Locator Map at /locators/<portal>/locator-map.json
   — Maps each UI element to: CSS selector, data-testid, ARIA role, fallback XPath
   — Versioned: every update appends a changelog entry, never overwrites history
   — New elements added; deprecated elements flagged, not deleted
7. Produces handoff note for QA Agent: changed components, new routes, removed elements, locator health status

### Phase 3 — Manual QA Track (QA Agent)

8. QA Agent receives approved TestCases.xlsx (Sheet 1) and handoff note from Tech Lead Agent
9. Calls skill: test-case-reviewer to validate coverage and traceability before proceeding
10. Updates or creates test case artefacts in manual-qa-repository/01-test-cases/<portal>/<module>/
    — TestCases.xlsx (Sheet 1: manual, Sheet 2: automation candidates)
    — test-data-spec.md
11. Updates manual-qa-repository/ tracking docs: SPRINT_LOG.md, TASK_TRACKER.md, DOCUMENTATION-TRACKER.md
12. Updates test data factories in automation-repository/test-data/factories/ if data structure changed
13. Output: approved manual test cases, test data spec, updated tracking docs

### Phase 4 — Automation QA Track (QA Agent)

14. QA Agent owns ALL automation code — creation, scaffolding, editing, archival, execution
15. Picks up Sheet 2 (automation candidates) from Phase 3 + updated locator maps from Phase 2
16. Scaffolds any new spec files and POMs needed from templates/module-scaffold/ — never delegated to Developer Agent
17. Implements/updates all Page Object Model files in automation-repository/pages/<portal>/
18. Executes all six test types in order using the locator map and automation candidates:
    a. skill: run-e2e           — full user journey tests, toHaveScreenshot() at each step
    b. skill: run-ui-ux         — component rendering, responsiveness, accessibility, empty states
    c. skill: run-regression    — locked baseline comparison; fails CI on any drift
    d. skill: run-cross-browser — Chrome, Firefox, Edge via Playwright multi-browser runner
    e. skill: run-api-tests     — endpoint coverage mapped to FRD features
    f. skill: run-db-tests      — raw Sequelize queries from db/queries/, query-level audit trail
19. Calls skill: generate-report after all suites complete
20. Calls skill: generate-user-manual assembled from E2E screenshots + BRD/FRD user journeys
    — Saved to manual-qa-repository/03-user-manual/<portal>/<module>.md
21. Any E2E failure due to locator breakage triggers skill: e2e-self-healer before escalating
22. Posts stakeholder summary.md
23. If a failure requires source-code changes in the application, QA Agent documents it clearly
    and the user explicitly invokes Developer Agent for that task only

## Agents


All agents live in .claude/agents/. Each agent self-initialises on receiving a feature name or task trigger. Agents operate autonomously and notify only on: task complete, blocker encountered, or new undocumented module detected.

### BA Agent (ba_agent.md)

Role: Business analyst and documentation owner

Responsibilities:
- Read and interpret BRD/FRD for the given module from .claude/docs/hoabl-knowledge-base/
- Call skill: manual-tester to generate structured test cases (positive + negative) and test data specs
- Update .claude/docs/hoabl-knowledge-base/ when requirements change (triggered by sync pipeline Step 2)
- Flag any requirement that is ambiguous, missing, or contradicted by observed source code behaviour
- Produce: approved TestCases.xlsx, test-data-spec.md, requirement gap report

Does NOT: touch test files, source code, locator maps, automation scripts, or any implementation artefact.

### Tech Lead Agent (tech_lead_agent.md)

Role: Code archaeologist and locator authority

Responsibilities:
- Scan source code changes across all repos in source-code/ — Strapi folder excluded entirely
- Call skill: locator-map-builder to build and maintain the Element Locator Map per portal
- Call skill: e2e-self-healer proactively when locator breakage is detected in a diff
- Produce: change-manifest.json, updated locator-map.json per portal, handoff-note.md for QA Agent

Does NOT: touch test files, write or edit any test or automation code, scaffold POMs, or modify playwright.config.js.

### QA Agent (qa_agent.md)

Role: Test owner — sole owner of all manual QA artefacts and all automation code

Responsibilities:
- Receive approved TestCases.xlsx from BA Agent and locator map + handoff note from Tech Lead Agent
- Call skill: test-case-reviewer to validate coverage before any execution begins
- Own and maintain all artefacts in manual-qa-repository/ (test cases, tracking docs, user manuals)
- Scaffold new spec files and POMs from templates/module-scaffold/ when a new module is introduced
- Implement and maintain all Page Object Model files in automation-repository/pages/<portal>/
- Update automation-repository/playwright.config.js for new portals or browser targets
- Execute all six test type skills in sequence (Phase 4)
- Call skill: generate-report and skill: generate-user-manual post-execution
- Move deprecated test specs to tests/archived/ (never delete)
- Post stakeholder summary; escalate application-level failures to user for explicit Developer Agent invocation
- Produce: all manual QA artefacts, all test specs, all POMs, HTML/JSON reports, user manuals, stakeholder summary

### Developer Agent (developer_agent.md)

Role: Application source-code engineer — invoked explicitly by the user only

Responsibilities:
- Make source-code changes to the application repos when explicitly instructed by the user
- Provide documentation, architectural notes, or technical context to other agents when required
- Read codebase to answer technical questions from other agents (read-only unless explicitly instructed)

Does NOT: touch test files, POMs, playwright.config.js, locator maps, TestCases.xlsx, manual-qa-repository/, or any test or QA infrastructure — ever, under any circumstances, unless the user explicitly scopes a task to it. Developer Agent's default posture is read-only on the entire codebase. All test and QA implementation is owned by QA Agent.

## Skills Catalogue


All skills live in .claude/skills/. Skills are composable — agents call skills as sub-steps.
Skills never call agents. Agents call skills. This hierarchy is non-negotiable.

Each skill file must define: name, description, trigger conditions, inputs, outputs, example invocation.

### 1. manual-tester
Purpose: Generate structured test cases from BRD/FRD for a given module
Inputs: module name, portal name, BRD/FRD section path
Outputs: TestCases.xlsx (Sheet 1: manual positive/negative per user journey, Sheet 2: automation candidates), test-data-spec.md
Called by: BA Agent

### 2. test-case-reviewer
Purpose: Review test cases for coverage completeness, BRD/FRD traceability, and edge case gaps
Inputs: TestCases.xlsx path, BRD/FRD section path
Outputs: review-report.md (gaps flagged, approval status per case, coverage %)
Called by: QA Agent (on BA Agent output, before any execution)

### 3. locator-map-builder
Purpose: Build and maintain the Element Locator Map for a portal
Inputs: portal name, source code path, approved test case list
Outputs: updated /locators/<portal>/locator-map.json with versioned changelog entry
Behaviour: add new elements, flag deprecated ones, never overwrite history
Called by: Tech Lead Agent

### 4. e2e-self-healer
Purpose: Detect broken locators after code changes and auto-repair them in spec files and locator map
Inputs: failing spec file or broken locator key, source code diff
Outputs: healed spec file, updated locator map entry, diff report of changes made
Trigger: E2E failure due to element-not-found or locator mismatch; or proactively by Tech Lead Agent on a breaking diff
Called by: QA Agent (on failure), Tech Lead Agent (proactively)

### 5. run-e2e
Purpose: Execute E2E tests for a portal/module; capture screenshots at each step
Inputs: portal name, module name, locator map path, automation candidates (Sheet 2)
Outputs: Playwright results, toHaveScreenshot() snapshots per step, step-level pass/fail log
Config: Chrome primary, single worker by default, expandable for parallel runs
Called by: QA Agent

### 6. run-ui-ux
Purpose: Assert component rendering, responsiveness, accessibility, error/empty states
Inputs: portal name, module name, design spec references from BRD/FRD
Outputs: UI assertion results, ARIA/keyboard navigation report, responsive breakpoint report
Called by: QA Agent

### 7. run-regression
Purpose: Compare current run against locked baseline snapshots; fail CI on any drift
Inputs: portal name, baseline snapshot path
Outputs: regression diff report (visual + assertion), list of broken flows
CI behaviour: called by CI pipeline on every push/PR; fails pipeline if any regression detected; baseline updated only after a reviewed and approved release
Called by: QA Agent

### 8. run-cross-browser
Purpose: Run full E2E suite across Chrome, Firefox, Edge
Inputs: portal name, module name
Outputs: per-browser pass/fail report, browser-specific failure details with reproduction steps
Called by: QA Agent

### 9. run-api-tests
Purpose: Test all REST/WebSocket endpoints mapped to the module's FRD features
Inputs: module name, API base URL (https://uat-api.xrportal.in/), FRD endpoint list
Outputs: status code assertions, schema validation, response time report, auth guard results
Exclusions: skip endpoints not integrated with any portal; skip all LSQ endpoints
Called by: QA Agent

### 10. run-db-tests
Purpose: Execute database-level assertions using raw Sequelize queries from db/queries/
Inputs: module name, query file list, DB connection config from .env
Outputs: per-query audit trail — exact query, expected output schema, actual result, anomaly diff
Rules: QueryInterface + raw SQL only; no ORM models; never inline queries; one file per domain entity
Called by: QA Agent

### 11. generate-report
Purpose: Compile all test results into structured HTML + JSON report with executive markdown summary
Inputs: all test run results from skills 5–10
Outputs: reports/[run-id]/report.html, report.json, summary.md
Contents: pass/fail counts, coverage %, screenshots, anomaly highlights, BRD/FRD traceability matrix
Called by: QA Agent

### 12. generate-user-manual
Purpose: Auto-generate module user guide from E2E screenshots and BRD/FRD user journeys
Inputs: module name, E2E screenshot folder, BRD/FRD user journey section
Outputs: manual-qa-repository/03-user-manual/<portal>/<module>.md with annotated screenshots per step
Called by: QA Agent

### 13. sync-and-update
Purpose: Full four-step pipeline — detect code changes, update docs, sync manual QA, sync automation
Trigger: npm run sync  OR  claude skill run sync-and-update
See Section 8 for full pipeline definition.

## Test Coverage Requirements


For every module in each portal, all six test types are mandatory. All tests cover positive (happy path) and negative (edge/error/boundary) scenarios derived exclusively from BRD/FRD user journeys. Every test must carry a BRD/FRD requirement ID.

### 6.1 End-to-End (E2E) Tests
- Full user journeys from entry to completion per FRD
- Multi-step flows, inter-portal data dependencies, session management
- State persistence and rollback on failure
- toHaveScreenshot() at every significant step
- Executed via skill: run-e2e — npm run test:e2e

### 6.2 UI/UX Tests
- Correct rendering of all UI components per design spec
- Responsive behaviour, form validations, error messages, empty states
- Accessibility: ARIA roles, keyboard navigation, focus management
- Loading states, skeleton screens, toast/notification behaviour
- Executed via skill: run-ui-ux — npm run test:ui

### 6.3 Regression Tests
- Locked baseline snapshots of all critical user flows per portal
- CI calls skill: run-regression on every push/PR — fails pipeline on any drift
- Baseline updated only after a reviewed, approved release
- Prioritise flows involving shared backend services across portals
- Executed via skill: run-regression — npm run test:regression

### 6.4 Cross-Browser Tests
- Chrome (primary), Firefox, Edge — Playwright multi-browser runner
- Per-browser pass/fail with reproduction steps for browser-specific failures
- Executed via skill: run-cross-browser — npm run test:chrome / test:firefox / test:webkit

### 6.5 API Tests
- All REST/WebSocket endpoints integrated with portals (per FRD)
- Base URL: https://uat-api.xrportal.in/
- Skip endpoints not connected to any portal; skip all LSQ endpoints
- Assert: status codes, response schema, response time, auth guards, rate limits
- Negative: invalid tokens, malformed payloads, missing required fields
- Each API test maps to a BRD/FRD requirement ID
- Executed via skill: run-api-tests — npm run test:api

### 6.6 Database Tests
- All queries in db/queries/ — never inline
- Sequelize QueryInterface + raw SQL only — no ORM models
- One file per domain entity (booking.js, inventory.js, user.js, [entity].js)
- Each query file: purpose comment, expected output schema, documented anomaly conditions
- Report: exact query, expected vs actual output, anomaly diff
- Executed via skill: run-db-tests — npm run test:db

## Sync Pipeline: Code → Docs → Tests


Trigger: npm run sync   OR   claude skill run sync-and-update

Four-step pipeline. Each step must complete and produce its output before the next agent begins.
Steps 3 and 4 are explicitly separated: Step 3 is the Manual QA track, Step 4 is the Automation QA track.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
STEP 1 — Tech Lead Agent: Detect Changes + Update Locator Map
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Read sync/last-synced-commits.json — retrieve last synced commit SHA per repo
2. Run git diff <last-sha>..HEAD across all repos in source-code/
   Strapi folder excluded entirely from all scans — no exceptions
3. Identify: files changed, UI components modified, routes added/removed,
   API endpoints changed, new modules detected
4. Call skill: locator-map-builder — update /locators/<portal>/locator-map.json for all affected portals
5. Call skill: e2e-self-healer — auto-repair any locator breakage detected in the diff
6. Update sync/last-synced-commits.json with new commit SHAs
7. Produce:
   → change-manifest.json       (portal, module, change type per file)
   → updated locator-map.json   (per affected portal, versioned)
   → handoff-note.md            (for BA Agent: what changed, which modules, UI/API context)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
STEP 2 — BA Agent: Update BRD/FRD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Receive change-manifest.json and handoff-note.md from Tech Lead Agent
2. Identify which BRD/FRD sections are affected:
   — new feature → add new section
   — modified flow → update section with diff annotation
   — deprecated behaviour → mark section deprecated (do not delete)
3. Generate a diff-style update proposal for each affected section
4. On approval: write updated docs to .claude/docs/hoabl-knowledge-base/
5. Produce:
   → updated BRD/FRD files
   → doc-change-summary.md      (for QA Agent: modules changed, nature of change)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
STEP 3 — QA Agent · MANUAL QA TRACK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Inputs: doc-change-summary.md from BA Agent

3a. Test Case Update
    — Map doc changes to existing TestCases.xlsx files in manual-qa-repository/01-test-cases/
    — Modified modules: update affected sheets in-place
    — New modules: call skill: manual-tester → generate new TestCases.xlsx

## Constraints & Non-Negotiables


1. LeadSquared (LSQ): excluded entirely from all tests, reports, and generated docs.
   No credentials, no direct API calls to LSQ anywhere in the framework.

2. Strapi admin: out of scope for direct testing. Test only downstream effect on the four portals.
   The Strapi folder is excluded from all source-code scans — no exceptions.

3. Playwright config: JavaScript (CommonJS), Playwright 1.58.2, Chrome primary, single worker by default,
   toHaveScreenshot() for all visual regression, POM architecture mandatory across all portals.
   playwright.config.js owned and maintained by QA Agent.

4. DB tests: Sequelize QueryInterface + raw SQL only. No ORM models.
   Queries live exclusively in db/queries/ — never written inline anywhere.

5. Element Locator Map: maintained exclusively by Tech Lead Agent via skill: locator-map-builder.
   Never edited manually, inline, or by any other agent.

6. BRD/FRD: sole source of truth for all test case generation.
   No feature is tested unless it is documented in .claude/docs/hoabl-knowledge-base/.

7. Traceability: every test case must carry a BRD/FRD requirement ID.
   Traceability matrix is included in every generated report.

8. Agent ownership of test code and QA artefacts: QA Agent is the sole owner of all test specs,
   POMs, playwright.config.js, TestCases.xlsx, manual-qa-repository/, and all QA infrastructure.
   Developer Agent never touches any of these, under any circumstances.

9. Developer Agent scope: read-only by default. Makes source-code changes only when the user
   explicitly instructs it for a specific task. May provide docs or technical context to other agents.
   Never initiates test-related or QA-related work.

10. Skills do not call agents. Agents call skills. Non-negotiable in every agent markdown file.

11. Test and case archival: deprecated test specs → tests/archived/.
    Deprecated manual test cases → manual-qa-repository/01-test-cases/archived/.
    Nothing is ever deleted.

12. Sync pointer: sync/last-synced-commits.json updated at end of every successful sync run
    to prevent redundant re-scans on the next trigger.
