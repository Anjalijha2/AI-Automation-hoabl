# Feature: View Milestones (from Customers Row)

## 1. Objective
Allow admins to drill into the full milestone payment schedule for a buyer's booked unit directly from the Customers registration table, so they can review what has been paid, what is pending, and what is outstanding for each construction-linked milestone.

This is primarily a read-and-review surface. Admins do not create or edit the milestone schedule from here — the schedule is generated by the system after KYC submission per `SHARED-WF-milestone-payments`. The page does expose an "Offline Payment" action on payable milestones (admin-recorded offline collection), which mirrors the SM portal offline payment flow.

## 2. Scope
- Row-level action available via the three-dot (…) action menu in the Customers registration table.
- Opens a dedicated milestone schedule page for the selected `registrationUnit`.
- Includes a side drawer for transaction details (read) and offline payment capture (write).

## 3. Eligibility / Preconditions
1. **Row status:** Menu item visible only when the row is a Booked unit — i.e. `status = 'WINNER'` AND `allocationTransactionId IS NOT NULL` (`isBooked` flag in CustomerTable).
2. **KYC dependency:** A milestone schedule only exists once the buyer has submitted KYC. Until then, the table on this page will be empty even though the menu item is shown.
3. **URL parameters:** Page requires `rn` (unit registration number) and `uid` (unit id) — both injected by the navigation click; opening the URL without these returns an empty state.

## 4. UI Changes

### 4.1 Menu Entry
- New entry in the row's three-dot (…) dropdown labelled **"View Milestones"** (key `view-milestones`).
- Selecting it navigates to `/admin/milestone?rn=<unitRegistrationNumber>&uid=<unitId>`.

### 4.2 Milestone Page (`/admin/milestone`)

| Element | Behaviour |
|---------|-----------|
| **Back to Customer Listing** link | Top-left; returns to `/admin/dashboard?scrollTo=customerTable` |
| Page title | "Milestone Payment Schedule" with green left bar |
| Header card | Two read-only fields: **Registration No.** (from `rn`), **Unit No.** (from `fetchData.unitNumber`) |
| Milestone table | One row per milestone; columns described in §4.5 |

### 4.3 Transaction Details Drawer (right-side, width 800px)
- Triggered by **View** button in the table's "DETAILS" column when the milestone has a `transactionId`.
- Title: "Transaction Details".
- Renders `ViewDetails` component with the milestone record and a list of payment transactions for that milestone.
- Per-transaction classification logic:
  - If only one non-GST entry matches the principal collection, or only one HC entry matches total — labelled **Full Payment**.
  - Otherwise non-GST and HC entries are labelled **Partial Payment 1, 2, …** in sequence.
  - GST-only entries are always labelled **Full Payment**.

### 4.4 Offline Payment Drawer (right-side, width 600px)
- Triggered by **Offline Payment** button in the "ACTION" column (see §6 eligibility).
- Title: "Offline Payment".
- Renders `PayDrawer` — captures offline payment for the milestone and posts via `apiUrls.adminMilestonePaymentOffline` (multipart/form-data). Full field schema documented in §5 below.

### 4.5 Milestone Table Columns

| Column | Source Field | Notes |
|--------|--------------|-------|
| MILESTONE | `milestone` | HTML-rendered name; tooltip slot reserved for agreement-change notes (currently empty stub) |
| % DUE | `dues` | HTML-rendered |
| GST | `gst` | Plain string |
| `<unitName>` / PRINCIPAL | `principalCollection` | Column header switches to uppercase `unitName` from `fetchData` when present, else "PRINCIPAL" |
| TOTAL AMOUNT | `totalAmount` | Rendered only if `startDate` is in the past; otherwise `-` |
| TOTAL OUTSTANDING | `totalOutstanding` | Rendered only if `startDate` is in the past; otherwise `₹ 0` |
| PAYMENT STATUS | derived | See §5.2 |
| ACTION | derived | "Offline Payment" button (see §6) |
| DETAILS | `transactionId` | "View" button if `transactionId` present |

## 5. Form Details

### 5.1 Offline Payment Drawer (`PayDrawer`) — Field Schema

The Offline Payment drawer posts a **multipart/form-data** payload to `apiUrls.adminMilestonePaymentOffline` via `expressPostFormData`. The following 11 fields are sent on every submission (source: `PayDrawer.jsx` L105–138, `MilestonePage.jsx` L142–157):

| # | Field | Origin | Type | Required | Validation / Notes |
|---|-------|--------|------|----------|--------------------|
| 1 | `registrationNumber` | URL query param `?rn=...` (selectedRecord) | string | Yes | Injected from page route; not user-editable |
| 2 | `milestoneKey` | `selectedRecord` (current milestone row) | string | Yes | e.g. `ml-or`, `ml-hcf` |
| 3 | `milestoneId` | `selectedRecord` | integer | Yes | — |
| 4 | `amount` | Form field "Amount" (InputNumber) | number | Yes | Must be > 0; cannot exceed payable outstanding; in GST mode must equal `gstOutstanding` exactly (tolerance 0.01) |
| 5 | `paymentType` | Auto-computed by `calculatePaymentType()` | integer code (1–5) | Yes (auto) | `1` = Principal Full, `2` = Principal Partial, `3` = GST-only, `4` = HCF Full, `5` = HCF Partial |
| 6 | `paymentMethod` | Form field "Payment Method" (Select) | string | Yes | Options: `NEFT`, `Cheque`, `Cash`, `CC` (Credit Card), `DC` (Debit Card), `UPI` |
| 7 | `transactionId` | Form field "Transaction ID" (Input) | string | Yes | — |
| 8 | `transactionDate` | Form field "Transaction Date & Time" (DatePicker) | string | Yes | Format `YYYY-MM-DD HH:mm:ss`; future dates blocked (`disabled if after dayjs()`) |
| 9 | `comments` | Form field "Comments (Optional)" (TextArea) | string | No | Max 500 chars; sent as empty string when absent |
| 10 | `paymentProof` | Upload (single file) | File | Yes | `accept=.pdf,.jpg,.jpeg,.png`; max 1 file; submit blocked if empty (helper text says "Max 5MB" but client does NOT enforce size — informational only) |
| 11 | `paymentFor` (radio — conditional) | "Principal" / "GST" radio | string | Conditional | Rendered only when milestone is NOT HCF AND at least one of principal/GST outstanding > tolerance. Drives whether `amount` targets principal vs GST collection. |

**UI logic notes:**
- For HCF milestones (`milestoneKey === 'ml-hcf'`): no "Payment For" radio is shown; `amount` is freely editable; `paymentType` is `4` (full) if `amount >= total outstanding` else `5` (partial).
- In GST mode: `amount` is auto-set to `gstOutstanding` and the input is **disabled** (must equal `gstOutstanding`).
- Payment Proof helper text: `Allowed formats: PDF, JPG, PNG (Max: 5MB)`. The `accept` attribute enforces format client-side; file size is NOT enforced client-side.

### 5.2 Payment Status Pill Rules (frontend-derived)

Source: `MilestonePage.jsx` L218–253 (PAYMENT STATUS column render).

Inputs:
- `total = rupeeToNumber(item.totalAmount)`
- `outstanding = rupeeToNumber(item.totalOutstanding)`
- `balance = total − outstanding` — **semantically: amount already paid** (variable name in source is misleading but the labels render correctly)

| Condition | Status Pill | Icon |
|-----------|-------------|------|
| `startDate` is in the future (`!checkPaymentDate(startDate)`) | (cell renders nothing — `null`) | — |
| `milestoneKey === 'ml-or'` AND `total === 0` | `-` (dash, no pill) | — |
| `balance <= 0` (nothing paid yet) | **Pending** | clock (`IoMdTime`) |
| `0 < balance < total` (partially paid) | **Partial Payment** | card (`IoMdCard`) |
| `balance >= total` (fully paid) | **Paid** | check-circle (`IoMdCheckmarkCircle`) |

> **Clarification (resolved 2026-05-21):** The logic is NOT inverted. The variable named `balance` in source code actually holds *amount paid* (`total − outstanding`). Test assertions must key off `paid vs. outstanding`, not off the misleading variable name. There is no code bug here.

## 6. Validations & Business Rules

### 6.1 Action Eligibility

**Offline Payment button** — rendered when **all** of:
- `record.milestoneKey !== 'ml-or'` OR `total !== 0`
- `startDate` is in the past
- `outstanding > 0`

**Transaction Details View button** — rendered when `transactionId` is present on the milestone row.

### 6.2 Business Rules
1. View Milestones is available only on Booked rows (`isBooked === true`); the menu item is not rendered otherwise.
2. Milestone schedule is read-only by design — admins cannot add, delete, or reorder milestones from this view.
3. Status pills, payable state, and outstanding display all hide for future-dated milestones (`startDate` in the future).
4. Special-case milestone `milestoneKey = 'ml-or'` with `total = 0` is treated as not-applicable — no status pill, no action button, no detail link.
5. The View Milestones page does NOT validate whether KYC has been submitted before opening — empty table is the expected state when KYC is not yet done. (Cross-reference: `SHARED-WF-milestone-payments` §3 — schedule generated on KYC submission.)
6. Offline Payment created here flows into the same milestone tracking records as SM Portal offline payments.
7. **GST-mode amount lock:** When the admin selects "GST" in the Payment For radio, the `amount` field auto-populates from `gstOutstanding` and is disabled — admin cannot under- or over-pay GST.
8. **Future-date guard on transaction date:** The Transaction Date & Time picker disables any date after `now()` — admins cannot back-date into the future.
9. **`paymentProof` is mandatory:** Submit button is blocked client-side when no file is attached (PayDrawer L106–109).

## 7. System Actions

### 7.1 On Page Load
- `GET apiUrls.adminUserUnitDetail?registrationNumber=<rn>&unitId=<uid>` — returns `{ unitNumber, unitName, unitData[] }` where `unitData` is the milestone list.

### 7.2 On View (Transaction Details)
- `GET apiUrls.adminMilestoneTransactionDetail` with query:
  - `transactionId` = `record.transactionId`
  - `initialPaid = true` when row index `< 2` (first two milestones — registration + booking token)
  - `isAllocation = true` when row index `=== 1`
  - `registrationNumber` = `rn`
- Response classified into Full / Partial Payment N as in §4.3.

### 7.3 On Offline Payment Submit
- `POST apiUrls.adminMilestonePaymentOffline` (multipart/form-data) with the 11-field payload defined in §5.1.
- On success: toast "Offline payment submitted successfully", page refetches via `fetchDetails()`.
- On failure: toast with server `message` or fallback "Failed to submit payment".

### 7.4 Navigation
- "Back to Customer Listing" → `/admin/dashboard?scrollTo=customerTable`.

## 8. Notifications

**Buyer-facing notifications: NONE.**

Source scan confirms (`registration-unit.service.js`, full backend `kaleyra|sendSms|sendWhatsapp|sendEmail|sendNotification` grep): the View Milestones page is a **read-only GET** — no mutation, no notification dispatch. The Offline Payment submission does not trigger any SMS, WhatsApp, or email to the buyer either. Admin-facing UI toasts only:

- Toast on transaction-detail fetch failure: "Failed to load transaction details".
- Toast on unit-detail fetch failure: server `message` or "Failed to fetch unit details".
- Toast on offline payment submit success: "Offline payment submitted successfully".
- Toast on offline payment submit failure: server `message` or "Failed to submit payment".

## 9. Audit & Logging

- **GET actions** (page load, transaction detail fetch) — no audit log emitted; read-only.
- **Offline Payment submit** — backend audit log expected on the milestone-payment service. Frontend does not emit; only `logger.info` traces observed in the closest related service flows. Detailed audit payload (admin user, milestone ID, amount, payment method, timestamp) is enforced by the backend offline-payment service.

## 10. How to Use

1. **Find a booked registration:** In the Customers table, locate a row whose Allocation Status is "Booked Online" or "Booked Offline" (i.e. a unit is allotted and a confirmation transaction exists).
2. **Open the action menu:** Click the three-dot (…) icon in the Actions column. **View Milestones** appears only for booked rows.
3. **Select "View Milestones":** The Milestone Payment Schedule page opens at `/admin/milestone?rn=…&uid=…`.
4. **Read the schedule:** The table lists every milestone for the unit. Future milestones show no status or amount. Past milestones show Paid / Partial Payment / Pending. The special row `ml-or` with zero total renders blank cells.
5. **View transaction detail:** Click **View** in the DETAILS column on any milestone that already has a transaction. The right-side Transaction Details drawer opens with each payment classified as Full Payment or Partial Payment 1, 2, ….
6. **Record an offline payment (optional):** On any past-dated milestone with outstanding balance, click **Offline Payment** in the ACTION column. The Offline Payment drawer opens. Complete the form:
   - Select **Payment For** (Principal / GST) — appears only for non-HCF milestones when both legs have outstanding.
   - Enter **Amount** (auto-locked in GST mode).
   - Pick **Payment Method** (NEFT / Cheque / Cash / CC / DC / UPI).
   - Enter **Transaction ID**.
   - Pick **Transaction Date & Time** (cannot be in the future).
   - Optionally add **Comments** (max 500 chars).
   - **Upload Payment Proof** — required; PDF / JPG / JPEG / PNG; one file.
   - Click **Submit**. On success the toast "Offline payment submitted successfully" appears and the schedule refreshes.
7. **Return to Customers:** Click **Back to Customer Listing** at the top-left. The dashboard reopens and scrolls back to the customer table.

> **Note:** If the milestone table is empty for a booked unit, the most likely cause is that the buyer has not yet submitted KYC. The system generates the milestone schedule only after KYC submission.

> **Note:** Recording an offline payment here does NOT notify the buyer by SMS, WhatsApp, or email. The buyer will see the updated payment status the next time they refresh their portal view.
