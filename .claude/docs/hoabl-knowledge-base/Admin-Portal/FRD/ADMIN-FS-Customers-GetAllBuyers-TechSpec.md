| Value | Predicate |

## 3. Export (`isDownload`) Behaviour — CRITICAL CORRECTION

**This section explicitly corrects prior BRD/FRD claims that "export ignores filters."**

### What the code actually does

- Line 125: `const paginationConfig = isDownload === '1' ? {} : limitOffset(limit, page);`
- This is the **only** branch on `isDownload` that affects the result-set scope. When `isDownload === '1'`, the spread `...paginationConfig` (line 643) inserts no `limit`/`offset` → all matching rows are returned.
- All filter blocks (lines 280–516) execute **unconditionally** with respect to `isDownload`. They push into `conditions`, which is attached to `where[Op.and]` at line 514–516 before the single `findAndCountAll` call.
- The Excel build branch (lines 697–end) consumes `updatedRegistrations` — the exact same filtered/sorted row collection used by the table response, just unpaginated.

### Correct, normative statement (to replace any contrary BRD/FRD text)

> **Export respects all active filters.** The `isDownload=1` flag only removes the pagination limit so that the Excel includes every row matched by the current filter/sort criteria. With no filters applied, the export contains all rows for the project; with filters applied, the export contains exactly the filtered set across all pages.

### Implications for QA

- Test cases that assert "Download returns all customers regardless of filter" are **incorrect** and must be updated.
- Expected behaviour: Apply filter F → download → Excel row count equals total filtered count (sum across all pages of the table view with the same filter applied).
- Sort order in Excel matches `sortKey`/`sortOrder` query params at the moment of export.

## 4. KPI Counts — Separate Query, NOT Affected by Filters

KPI values returned in `adminKpi` (lines 201–209) are sourced from a **separate** aggregate query (lines 127–193) that runs BEFORE the filter-condition block is built.

### KPI query characteristics

- Model: `RegistrationUnit.findAll` with `attributes` = list of `fn('SUM', literal('CASE WHEN ...'))` expressions.
- `where`: only `{ projectId }` on the joined `Registration.scope('withRefunded')`; nested `User` join is `required: true` (any user). **No** filter conditions from the table query are applied.
- `raw: true`; the result is a single aggregate row.

### Returned counts

| Key | Definition |
|---|---|
| `registeredCount` | `SUM(CASE WHEN RegistrationUnit.status != 'REFUND' AND registration.status != 'REFUND' THEN 1 ELSE 0 END)` |
| `refundedCount` | `SUM(CASE WHEN RegistrationUnit.status = 'REFUND' THEN 1 ELSE 0 END)` |
| `waitlistCount` | `SUM(CASE WHEN RegistrationUnit.status = 'WAITLIST' AND RegistrationUnit.available_for_allocation = 0 THEN 1 ELSE 0 END)` |
| `kycPendingCount` | `SUM(CASE WHEN RegistrationUnit.status = 'WINNER' AND RegistrationUnit.is_kyc_submitted = 0 THEN 1 ELSE 0 END)` |
| `confirmedCount` | `SUM(CASE WHEN RegistrationUnit.status = 'WINNER' AND RegistrationUnit.is_kyc_submitted = 1 THEN 1 ELSE 0 END)` |
| `activeTower` | `Tower.count({ distinct: true, col: 'towerId', where: { isActive: 1 } })` (lines 195–199) — separate from the aggregate query |

> A previously-defined `allotedCount` literal is present but commented out (lines 153–161, 203). It is **not** returned in the response.

### Normative statement

> **KPI cards on the Customers page always reflect global, project-scoped counts.** They are NOT affected by any active table filter, search, or sort. The current implementation cannot recompute KPIs against the filtered set without a code change.

### 7.2 Behavioural risks worth flagging to BA/QA

1. **`globalSearch` is phone-only.** Any test or BRD line that says "search across name / registration / unit / tower" is wrong against the current implementation.
2. **`hasHomeLoan=true` semantics narrowed.** It now strictly means `HomeLoan.status='completed'`; the original two-branch loan-type/step logic was removed.
3. **`paymentStatus` and `kycStatus` values are space-containing and case-sensitive** (`Paid`, `Pending`, `KYC Completed`, `KYC Pending`). UI must URL-encode and send exact strings; comma-separated multi-select sends e.g. `KYC Completed,KYC Pending`.
4. **`isDownload` strict string `'1'` comparison.** Frontend must send literal `'1'`. `true`, `1`, `'true'`, `'yes'` will silently fall through to the table branch.
5. **`projectId` is fixed per environment** (`production ? 1 : 2`). Cross-project export is not supported.
6. **`Alloted` derived status depends on a live campaign lookup** (lines 232–272). If no live campaign exists, `campaignAllotedRegistrationUnitIds` is empty and filtering by `alloted` returns no rows (`IN [-1]`).
7. **Default sort silently overrides invalid `sortKey`** — falls through `default:` to `RegistrationUnits.id DESC` regardless of `sortOrder`. Tests asserting `ASC` order with an invalid sortKey will fail.
8. **`refundedCount` KPI counts only `RegistrationUnit.status = 'REFUND'`**, but `registeredCount` excludes both `RegistrationUnit.status='REFUND'` AND `registration.status='REFUND'`. This asymmetry is intentional per the `withRefunded` scope but should be documented in BRD.
